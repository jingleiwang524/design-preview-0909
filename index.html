问题建议规则例子为什么这样定
评审针对哪个版本 评审对象是一个具体修订，不是资产名。提交评审时把当前内容哈希固定下来，评审页显示这个哈希。建议、待确认 lateral-clearance 提交评审时哈希 a91f…，评审记录写「批准 a91f…」，不是「批准 lateral-clearance」。 正式站已经在用内容哈希（场景详情、配置版本历史都有），不需要新造标识。
改了还算批准吗 内容哈希变了，批准即失效，退回草稿并注明「内容已变更，需重新提交」。评审意见保留可见。建议、待确认 评审通过后又改了一个阈值 → 哈希从 a91f… 变 c30d… → 状态回到草稿，历史里能看到上一轮为什么通过。 否则「已批准」会指向一份没人看过的内容，这是最容易出事的地方。
已发布版本能改吗 不能改，只能新发一个修订。而且发新版本不自动停用旧版本——新版只是多出一个可选版本， 旧版保持启用，直到有人显式停用它。建议、待确认 collision@1.0.4 要调口径 → 发 @1.0.5。此时 1.0.4 仍然是启用状态， 引用它的配置继续按它跑；换不换由各配置的负责人自己决定（见下一节）。 自动停用会在别人没准备好的时候悄悄换掉他的口径；而且只有允许两个版本并存，才可能做新旧版本对比。 指标注册表现在就是「不可变版本」，这条只是把已有做法写成规则并覆盖到场景。
Run 怎么记录实际输入 Run 保存时把实际使用的每个输入的精确标识写进快照，包括场景修订、场景集版本、判定标准精确标识。建议、待确认 正式站 Run 已记录评测配置 Develop / Latest · v3、计算器 collision@1.0.4、地图版本、镜像摘要、配置快照哈希；本期补的是场景修订和判定标准精确标识（现在这里显示的是一段描述文字）。 大部分已经有了。台架段自己就写着「本次运行冻结的用例与依赖版本」——本期是把同样的写法补到 SIL 段。

升级、停用、撤销是三件不同的事

这三个词经常混着说，但发起人、影响范围、对历史 Run 的处理都不一样。 上一版只写了「停用」，容易被读成「发新版就把旧版关掉」。发新版本本身不改变任何旧版本的状态。

动作谁发起它到底做了什么对已有引用对历史 Run
升级引用
引用方的动作		 引用它的那个对象的负责人（评测配置负责人、场景集维护人） 把某一处引用从旧版指向新版。逐处决定，平台不代劳、不批量替换。 只改这一处；其他引用不动。保存时显示范围变化（第 07 章）。 不影响。历史 Run 记录的是它当时实际用的版本。
停用版本
资产所有者的动作		 资产责任人 / 指标口径归口人 这一版不再出现在选择列表里，不能被新建的引用选中。已有引用不被强行切换。 继续可运行，但引用处标「所引用版本已停用，建议升级」。 不影响，也不重算。
撤销发布
例外动作		 资产责任人 + 归口人，必须写原因并进审计 用于「这一版有严重问题，不该再被任何人使用」。除停用的效果外，还禁止新 Run 使用它，包括已有引用。 引用处变成阻断项，必须先换版本才能再跑（与第 07 章保存前检查同一套阻断语义）。 历史 Run 结论保留、不删除、不重算，但结果页加一行「所用版本已撤销：@1.0.5，原因见审计」。
三者的共同规则：都不删除任何版本，历史永远可追溯；都在资产的修订历史里留一行； 只有撤销强制填原因。建议、待确认
需要研发确认的是撤销怎么落地——能不能在创建 Run 时真的拦住一个已撤销的版本，还是只能做界面提示。 工作量待研发估算

两条路径：自己验证，和让别人也能用

这是本方案最重要的一处结构。人工评审不是所有试跑的前置条件——开发者调自己的东西，用草稿直接跑就行， 这是正式站现在的做法（4 个已发布场景的来源都是 scene-draft:draft-…）。只有当这个资产要成为别人也会引用的正式资产时，才走校验、评审、发布。

路径 A · 自己验证（不需要评审）
谁在用：正在改场景或改计算器的开发者。目的是「我这版对不对」。
1上传成 草稿→ 2自动校验（有结论就够）→ 3用草稿创建 Run→ 4看结果，改，再跑
本期只补一件事：草稿卡片上把校验结论和失败原因显示出来， 并在这张卡片上直接给「用这个草稿试跑」的入口。但校验失败不是一概放行： 警告级不阻断试跑，结果里标明「输入来自带警告的草稿」；错误级连试跑也不放行—— 像「引用的载具配置版本不存在」这种，跑起来只会换来一次失败的运行，还占执行资源。
没有错误时，这个循环可以跑很多次，全程不需要任何人审批。
这条路径产出的 Run 不能作为对外结论或基线（第 09 章有对应的标注方式），但照常保留在历史记录里。
路径 B · 成为可复用的正式资产（需要评审）
谁在用：想让自己的场景/指标进入公共库、被评测配置引用的人。目的是「别人也能放心用」。
1草稿→ 2校验无错误（警告可带着提交）→ 3提交评审→ 4已发布→ 5已采用（被至少一个配置引用）→ 6已停用
有错误就不能提交评审，避免评审人替机器做检查； 只有警告时可以提交，但警告条目要原样显示在评审页上，由评审人决定接受还是打回。建议、待确认 评审对象是一个具体修订；提交后又改内容，批准即失效（见★全景图的四条最小版本规则）。
第 5、6 步是下一阶段：正式站现在有「已发布」状态和「生命周期：启用」列， 但没有「发布了却没人用」和「该停用了」的表达。下一阶段
第 6 步不会自动发生：发一个新版本不会把旧版本变成已停用。停用和撤销都是有人显式发起的动作， 和「升级引用」也不是一回事——三者的定义见 ★ 全景图。
两条路径共用同一个草稿对象，不是两套东西。同一张草稿卡片上有两个动作：「试跑」和「提交评审」。 路径 A 在没有错误时随时可用；路径 B 需要没有错误才亮起（警告不拦，只是要给评审人看）。这样开发者的日常迭代不会被评审拖住，而公共库的入口仍然有人把关。

无法判定的 Run 留在哪些统计里

上一版写的是「不计入趋势、不能作为基线」，这话太粗，会让一批 Run 从视野里消失。 正确的做法是分开说：历史记录和可靠性统计要留着（否则就看不见平台到底有多不稳），只有指标比较才需要过滤。

用途无法判定的 Run为什么
运行历史记录（运行列表）保留 发生过就是发生过。列表里能按结论筛，但默认不隐藏。
结果完整度统计保留，而且是主角 完整度就是用来衡量「有多少该出结果的没出」。把无法判定剔掉，这个指标就永远是 100%，等于骗自己。
运行可靠性统计保留，而且是主角 「最近 50 次里有几次没跑出结果、卡在哪个阶段」是平台自己的健康指标，也是要不要投人修环境的依据。
指标数值比较 / 趋势曲线按下面的有效条件过滤 没有数值的项没法画进曲线。但过滤要显式：图上写清「本区间 12 次运行，10 次有效」，不能默默丢掉。
作为基线被对比该项无效则该项不可比 不是整个 Run 不能当基线，而是它缺结果的那几项不能比。其他项照常可比。

「能进入指标比较」的有效条件（单独定义）

这一节是给第 10、11 章用的。有效性判断的最小单位不是 Run，是「场景 × 指标」这一格——这样一个 Run 里坏了一格，不会让整次运行作废。

一格要进入比较，必须说明
① 有数值计算器成功输出了这个字段。没输出就是无效。
② 指标计算器版本相同两边都是 collision@1.0.4 才能比数值。版本不同 → 标「计算口径不同，仅供参考」，不进趋势曲线。
③ 场景是同一个修订场景内容变了，数值不可比。这是本期要补场景修订号的原因。
④ 关键运行参数一致至少地图版本和车辆配置要一致。本轮实测到 run-b2ce0262 里四个场景用了两个不同地图版本，这种差异必须能被发现。
⑤ 单位一致注册表已经在展示字段单位（episodes / frames / count），照它校验。
注意：这五条里没有「必须有判定标准」。 一个指标只有计算器、没有判定标准时，数值照样有效、照样能比较和进趋势，只是不产生通过/失败、不进门禁分母。 真正不能进比较的是场景完全没有绑定指标——那种情况根本没有数值（第 05 章有两者的对照表）。

聚合口径按指标语义定，不套用同一个函数

「这个集合的 min_clearance 是多少」必须有明确答案，但答案取决于这个指标是什么语义。 上一版统一写成「放行取最差值、趋势取中位数」，对事件计数型指标是错的：三次里出现一次碰撞，中位数是 0，等于把事故抹平。 所以先分语义，再定聚合。

先分清是哪一层聚合，两层不共用一条规则： 层 1 · 单次 Run 之内——同一次运行里跨多个场景、或一个场景跨多个 episode，怎么合成一个数。 层 2 · 多次 Run 之间——同一条件重复跑，或按时间排开看趋势，怎么合成一个数。
这两层的正确答案可以完全不同：min_clearance 在层 2 取中位数是有意义的（同一个场景，反映稳定性）， 在层 1 跨 5 个不同场景取中位数没有物理意义（见本章末尾第 ② 条，建议层 1 不做跨场景合并，只列每一格）。 下面这张表定义的是层 2；层 1 默认不合并，逐场景列出。建议、待确认
指标语义例子层 2 · 进门禁怎么合层 2 · 趋势怎么合为什么不用另一种
① 事件计数越少越好，0 常常是硬要求 collision_count（episodes）、collision_frame_count（frames）——正式站注册表里现有的字段 出现过就算未通过：多次取最大值，或直接看「有没有任一次 > 0」。 写「N 次中出现 M 次」加累计次数，不画中位数曲线。 中位数和均值都会把偶发事故抹掉：0 / 1 / 0 的中位数是 0，看上去完全干净。
② 连续裕度有分布，越大（或越小）越好 min_clearance、max_overlap_count 这类连续量 取最差值（这里是最小值），与单次 Run 的口径一致。 取中位数，要求同条件 ≥3 次，并同时给范围；不足 3 次就列出每次的值，不给聚合数。 门禁用中位数会放过一次真实越界；趋势用最差值波动太大，画成曲线看不出方向。
③ 比率 / 覆盖本身就是分子分母 通过率、结果完整度、场景覆盖率 用合并后的分子分母重新算，不对百分比取平均。 始终带分子分母显示，例如「17 / 18 格」。 对百分比取平均，会让样本很少的那次拿到同样权重，得出一个谁都算不回去的数。
④ 耗时 / 资源观测用，不进门禁 Run 耗时（正式站已显示 41m 12s）、镜像构建时长 不进门禁。 中位数 + 最慢一次并列显示。 只看最慢一次，会把一次排队等待当成性能退化。
